1. The MDS only manages metadata, and after granting a capability the client exchanges data directly with the OSDs; so data bandwidth scales with the number of OSDs and the MDS does not become a bottleneck.
2. A capability is a permission the MDS grants a client on each inode (read, write, cache, buffer) and takes back when necessary. If the client does not respond within the set timeout, or its session expires, the MDS evicts it and puts it on the blocklist.
3. A standby is idle and must replay the whole journal when it takes over; a standby-replay continuously follows the journal of a specific rank and has a warm cache, so failover is faster.
4. Because the backtrace metadata of every file is written to the default data pool, and these small operations are inefficient on EC; add the EC pool as a second pool and use it with a layout.
5. When the metadata load (number of files, clients or operations per second) exceeds what one MDS can handle. The automatic balancer has a history of unstable migrations, and explicit pinning gives predictable behaviour.
6. The kernel client is faster but depends on the kernel version; ceph-fuse is slower but matches the Ceph version, is easier to debug, and its failures are limited to one process.
7. So that all Ganesha daemons have the same centralised configuration, and adding or moving a daemon needs no file synchronisation.
8. Because the client itself tracks usage and stops writing; with a delay it may write slightly beyond the cap, and a malicious client can ignore it.
9. The layout is recorded on a file when it is created and does not change where existing objects are; a rename only changes metadata. To move data, the file must be copied.
10. Running Spark, Trino or Hive on RGW through the S3A interface; for POSIX workloads, mounting CephFS directly.
