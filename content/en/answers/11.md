2. ceph-ansible is imperative and corrects the state only when the playbook runs; cephadm is declarative and continuous, keeps the desired state inside the cluster and constantly reconciles it with the actual state.
3. Because Umbrella images require a CPU at the x86-64-v3 level, and generic virtual CPU models may not advertise it.
4. It applies settings suited to one host (for example an OSD failure domain); a single-node cluster has no protection against host failure and is not suitable for practising failures.
5. Because it shows which OSDs will be created on which disks and prevents disks from becoming OSDs unintentionally.
6. Because virtual disks may present themselves as rotational or non-rotational regardless of the real hardware.
7. Ansible for the OS, packages, network, time and keys; cephadm for all Ceph daemons, specs and upgrades.
8. Using `cephadm adopt` (or the `cephadm-adopt.yml` playbook) to take over the daemons one by one, after practising in a lab and with a healthy cluster.
9. A circular dependency between Kubernetes and storage; it is reduced by separating the storage nodes, or by deploying Ceph outside Kubernetes and using external cluster mode.
10. It reveals unrecorded manual or automatic changes so that they are either brought back into Git or fixed.
