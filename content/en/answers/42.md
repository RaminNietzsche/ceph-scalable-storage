1. The commit happens only on the master zone, predecessor_uuid must equal the current period, and realm_epoch must be exactly one more than the current period's.
2. When the master zone changes; a new period is created with the first epoch and the mdlog starts with the new prefix `meta.log.<period>.`, so the zones must read the old period's log to its end and then move on to the new log.
3. It prevents changes from bouncing back and forth endlessly in active-active: the zones a change has passed through are recorded, and it is not sent to them again.
4. A bucket shard (bucket:instance:shard) and, when needed, its generation; that is, "something changed in this shard, read its bilog".
5. In `bucket.sync-status.<src-zone>:<bucket>:<shard>` (with the generation suffix if there is one), in the log pool of the destination zone.
6. So that one broken bucket does not stall the whole shard. The failed key is recorded in the error repo, that is the omap of the object `datalog.sync-status.shard.<zone>.<N>.retry`, and retried separately.
7. They ensure each shard has only one processor at any moment (the lease, with rgw_sync_lease_period), and the bid spreads the shards among the RGWs.
8. The source keeps the previous generation's bilogs; the destination finishes all shards of the old generation (shards_done_with_gen), then moves incremental_gen to the new generation with its new number of shards.
9. mtime (at one-second precision unless high precision), then zone_short_id, and finally pg_ver.
10. Metadata (users, buckets) is written only on the master; other zones forward the request to the master and receive the result through metadata sync.
