1. The entrypoint, named after the bucket, only points to the current instance; the instance (`.bucket.meta.<bucket>:<id>`) has all the properties and the index layout. A reshard creates a new instance with a new bucket_id and moves the entrypoint to it; the marker stays the same.
2. In InIndex mode: the byte 0x80, the prefix `0_`, then `index_ver` in the format `%011llu`, a dot, the OSD version, and a dot and the subop number.
3. To separate them from ordinary names: in UTF-8 no name starts with 0x80, so the first byte tells the key type. Listing must skip the 0x80 range because non-ASCII names sort after it.
4. `size` is the actual stored size (after compression or encryption) and `accounted_size` is the size the user sent and saw; quotas and statistics are based on the latter.
5. The tag stays in `pending_map`. When the tag is older than `rgw_pending_bucket_index_op_expiration` (120 seconds), the next listing reads the head with check_disk_state and updates or removes the entry with `dir_suggest_changes`. `bucket check --fix` does the same for all entries.
6. The object logical head, the pointer to the current version: a `1001_<name>` entry in the index (with a change log) and a data-less head object with the original name that has the `user.rgw.olh.*` xattrs.
7. It creates a new instance of type delete marker and makes it the current version with link_olh; no data is deleted, and a GET without a versionId returns 404.
8. In the STANDARD pool of the bucket's placement; with no data, only the manifest and xattrs. All the data is in tails in the COLD pool.
9. The md5 of the concatenation of the parts' binary ETags in order, as hex, plus `-` and the number of parts.
10. The upload was created in the new format (v2), and the parts' omap keys are `part.%08d` and therefore sorted in numerical order.
