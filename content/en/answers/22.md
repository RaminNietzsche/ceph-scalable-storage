1. Because a Transaction is atomic: the object data, xattrs, omap and the pg log entry become durable together or not at all. The backend (BlueStore, MemStore, SeaStore) also stays swappable.
2. The inputs are the object name, pool, namespace, snap and the current OSDMap, and the output is the pg, acting and primary. If the primary or acting set changes with a new map, the op is resent to the right OSD.
3. Because the shard is derived from the hash of the PG ID. This preserves the order of a PG's ops without coordination between shards.
4. Fast delivery of the message in the same network thread and queueing it in the shard. No blocking work or long lock may be done in it.
5. v is the current version and compat the lowest compatible decoder version. The block length is stored so that an old decoder skips the new fields.
6. On the direct path, data is written with aio to fresh space. With deferred, small data is first recorded in the RocksDB WAL and written later. On SSD a seek is not expensive, and the double write only adds write amplification.
7. When all acting members (and the primary itself) have committed the transaction; eval_repop checks this.
8. The cls method named `bucket_complete_op`, called through `UpdateIndex::complete`.
9. Because the client writes directly to the OSDs with Striper and Objecter. Without Fb, the client cannot buffer and every write goes synchronously to the OSD.
10. The `src/common/options/*.yaml.in` file at that version's tag (for example v20.2.0) in the ceph/ceph repository.
