1. Fewer network round trips, atomic execution inside the PG transaction, and less data transfer by processing next to the data.
2. Because the other object may be in a different PG and OSD, and the method runs only in the transaction context of its own object.
3. load_list decides which classes are loaded at all; default_list decides which are permitted with the generic caps (x, class-read, class-write).
4. After execution the OSD checks the num_write counter and returns -EIO, because a write operation must be processed, recorded and replicated as a write.
5. Only calling the add method of the numops class (within the specified match scope, for example the pool).
6. Because it makes running arbitrary code inside the OSD possible, and without a sandbox or timeout it can block the PG.
7. By building a custom image on top of the official same-version image that has libcls_*.so in osd_class_dir, upgrading to it or setting container_image to it, and then adding the class to the lists.
8. Registration changed from cls_register_cxx_method with explicit flags to ClassRegistrar and a typed ClsMethod with RD/WR/PROMOTE Tags.
9. Because it runs under the PG lock in the processing thread, the PG's other operations wait and slow ops appear.
10. librbd uses cls_rbd (and cls_lock, cls_journal); RGW uses cls_rgw, cls_rgw_gc, cls_2pc_queue, cls_fifo, cls_version, cls_refcount and cls_log.
