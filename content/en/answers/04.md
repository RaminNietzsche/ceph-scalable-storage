1. Because no data or persistent state is kept in the radosgw process itself; everything is in RADOS. So any number of instances can be put behind a load balancer, and the failure of one instance affects only its in-flight requests.
2. One head object (about the first 4 megabytes of data together with the metadata and manifest), several tail objects for the rest of the data, and an omap entry in one of the bucket index shards.
3. The index is kept in omap, which EC does not support; and every PUT and DELETE is an index update, so HDD latency directly becomes the latency of every operation.
4. It prevents index shards from growing too large (giant omap objects); when the number of objects per shard reaches `rgw_max_objs_per_shard` (default 100,000), the shards are increased automatically.
5. A tenant is a namespace for buckets and users; an account (since Squid) is an AWS-style unit of ownership whose root user manages its own users, groups, roles and policies with the IAM API.
6. A wildcard DNS record for the domain, setting `rgw_dns_name` (or hostnames in the zonegroup), and a wildcard TLS certificate.
7. In GOVERNANCE a user with the bypass permission can get around the lock; in COMPLIANCE no S3 user can delete the version or shorten the period until it ends.
8. Only the head object is removed immediately; the tails are handed to the garbage collector and removed after `rgw_gc_obj_min_wait`.
9. It lets an S3 client authenticate with EC2 credentials created in Keystone, with RGW validating them against Keystone.
10. Because Hadoop's traditional commit works by rename, which in S3 means copying and deleting every object; the S3A committers remove this cost with multipart uploads that are completed only at the final commit, and write the output safely and quickly.
